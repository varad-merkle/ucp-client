UCP Client

A working Universal Commerce Protocol (UCP) client over MCP, shopping across several real stores through an AI assistant
Team POC-5 · 4 members
Phase: client-side implementation
Updated 2026-10-23

UCP is an open standard that lets platforms and AI agents talk to online businesses in one common way: find out what a store supports, search its catalog, build a cart and run a checkout. This project is the client side of that conversation, built against live UCP-enabled stores rather than mocks.

Why we built it

POC-5's overarching goal is to build real understanding of UCP across our team of four: how discovery, capabilities, transports and the shopping flows work under the hood, and where the specification leaves decisions to the implementer.

What this phase delivers

Something demonstrable: a UCP platform client, with a chat front end, that discovers stores, searches them, keeps a cart per store and runs checkout up to payment. It is built with the official ucp_sdk models and follows the 2026-08-25 specification.

The problem it solves

A shopper asks for something in plain words. The client has to turn that into correct UCP calls to the right stores:

  • Which store? UCP tells you how to talk to a store you already know, but has no directory of stores and no field saying what a store sells. We keep a registry (merchants.json) with each store's categories, and the model picks the categories that match the request.
  • How to talk to it? Each store publishes /.well-known/ucp. The client reads it at startup (without following redirects, as UCP requires), checks the protocol version and finds the store's MCP endpoint.
  • Staying correct. Every call carries our agent profile in meta, idempotency keys where the spec needs them, and full-replacement updates for carts and checkouts.
  • Several stores at once. Each store owns its cart, checkout and payment, so the client keeps one cart per store and runs checkout one store at a time.

How it works

Frontendchat, product cards, carts, checkout card, protocol log
→
agent.pygpt-4.1 reads the request and picks tools and 1–3 categories
→
shop.pyroutes by category, keeps per-store carts and the open checkout
→
call_mcpadds meta, calls the store's MCP tool, parses and logs
→
UCP storescatalog, cart and checkout tools over JSON-RPC

The model decides; plain Python does every UCP call. A buyer profile in SQLite (profile_store.py) supplies currency, country and language, and pre-fills checkout details. Stores fetch our agent profile through an ngrok tunnel.

Run it

You need: Python 3.11+ and uv, Node.js for the frontend, an ngrok account (free tier is fine: one tunnel), and access to the dentsu AI gateway for the chat model.

  1. Install the backend. In the ucp-client folder: 
    uv sync
  2. Configure .env. Copy .env.example to .env and fill in the gateway settings, then add your ngrok token. Never commit .env. 
    MODEL_ENDPOINT, api_version, APIVERSION, SERVICE_LINE, BRAND,
PROJECT, AZURE_OPENAI_API_KEY, DEPLOYMENT   # dentsu AI gateway
NGROK_AUTHTOKEN=<your ngrok token>
  3. Start the client (port 7000). It creates the buyer profile database, opens the tunnel and discovers every store in merchants.json: 
    uv run python client.py
  4. Start the frontend in the separate ucp-frontend repo, then open http://localhost:5173: 
    npm install && npm run dev
  5. Try it. The terminal shows the model's categories (LLM tool: search_products) and the stores searched (Categories […] -> […]).
    a sofa for my living room → Furniture City, Pier 1 a queen mattress → Furniture City wool sneakers → Allbirds car cleaning products → Auto-Xpert a rug for the hallway → Pier 1

Checks: GET /api/health (stores online), GET /api/merchants (what discovery found), GET /api/exchanges (every UCP call, request and response). Tests: uv run pytest.

What we learned

  • Discovery covers how to talk to a store, not what it sells: the store registry and its categories are ours to maintain.
  • Real stores differ from the spec's examples: a store on an older UCP version used different tool arguments, so we left it out rather than add an adapter.
  • Carts and checkouts belong to one business and updates replace the whole object, so details are resent every time. Live testing, not the examples, surfaced the rest: rate limits, redirects, stores needing the buyer on their own page.

Current limits and next steps

  • Payment is switched off: checkout stops once the details are complete, so no real orders are placed.
  • Identity linking: OAuth account linking, needed to read orders, waiting on Shopify Dev Dashboard credentials.
  • Frontend: show the store name on cart and checkout cards.
  • Currency: one market setting applies to every store; per-store context would fix mixed USD/GBP pricing.
  • Model routing: run the example prompts above end to end and record how well categories are chosen.
